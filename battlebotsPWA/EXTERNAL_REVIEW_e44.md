# AI ROBOCLASH — External code review (build e44)

> Filed 2026-07-28. External reviewer, unsolicited. This document is the review
> *as received*; verification notes and our disposition live in
> `REVIEW_TRIAGE.md` alongside it. Do not edit this file — it is the record of
> what was claimed.

# Overall verdict
The project has **strong engineering intent**: explicit invariants, a deterministic fixed-step engine, a physical reference bank, component instances, data-driven competitions, and unusually good comments explaining past failures.
However, the current build is **not yet trustworthy enough for persistent careers or serious balancing**. The main issue is not messy code in the ordinary sense. It is that several boundaries are declared as strict—locked builds, WYSIWYG layouts, no-reward exhibitions, pure rendering—but are crossed in practice.
I found **three release-blocking defects**, several significant progression and simulation inconsistencies, and a structural problem: `app.js` has become an integration monolith where UI rendering, persistence, economy, competition state, geometry hydration and damage assignment can silently affect each other.

## Review scope
I:
* Read all supplied source files.
* Ran JavaScript syntax checks successfully on `app.js`, `data.js`, `engine.js` and `sw.js`.
* Loaded the engine separately in Node.
* Confirmed identical seed/build inputs replay deterministically in a targeted test.
* Reproduced the dead-battery `NaN` failure described below.
* Compared asset references with the service-worker precache list; the real referenced assets appear covered, apart from a comment placeholder.
* Could not run the official 644-check QC gate because the separate `roboclash-qc/` repository and its tools were not included.
* Did not complete a browser-level interaction test, so this is not a substitute for an end-to-end playtest.

# 1. Audit against the project's own principles
| Principle | Result | Finding |
| --- | ---: | --- |
| Engine pure, deterministic, no DOM | **Pass** | The separation is real, and the fixed-step, per-bot RNG and two-pass decision/integration design are sound. |
| Load order `data → engine → app` | **Pass** | HTML respects it. |
| Never bump `SAVE_V` without migration | **Fail** | README forbids this, but `SAVE_V=5` explicitly rejects and replaces every other schema. Existing careers can silently disappear. |

| `buildOfBot` / `layoutOfBot` are the only build/view assembly route | **Partial/fail** | The helpers exist, but home, VS and match startup still manually reconstruct flattened builds. The exact drift those helpers were introduced to prevent remains possible. |
| Calibration gives no purse or record | **Fail** | The generic match payout is credited before the calibration branch. |
| Free fight does not progress the player | **Fail** | A free-fight victory increments `S.beaten` and always awards bout money. |
| UI rendering should reflect, not alter, state | **Fail** | Rendering locked controls mutates pilot settings. |

The documentation is valuable, but it currently creates a dangerous sense of safety: some comments describe the intended invariant more confidently than the executing code warrants.

# 2. Highest-priority defects

## P0 — 100% worn battery corrupts the simulation with `NaN`
Wear can reduce battery efficiency to zero. The engine then creates a bot with `battery = batteryMax = 0`, and each tick calculates:
```js
const frac = bot.battery / bot.batteryMax;
```
That becomes `0 / 0`, after which acceleration, velocity and position become `NaN`. I reproduced this directly in Node after five ticks. Wear-to-zero is explicitly supported by the application. The engine applies that efficiency directly to energy, then divides by the resulting capacity.
**Fix immediately:**
```js
const frac = bot.batteryMax > 0
  ? clamp(bot.battery / bot.batteryMax, 0, 1)
  : 0;
```
But that is only the numerical guard. The technical inspection should also reject a required motor, battery or propulsion instance whose effective contribution is zero.

---
## P0 — Competition lock can fight as one bot and damage another
An engaged competition stores chassis, part definitions, counts, cosmetics and layout—but no persistent bot identity and no instance UIDs. The player remains free to change `S.activeBot`.
At match start:
* The locked definitions determine the fighting machine.
* Wear efficiency is read from `AB()`, meaning the **currently active bot**.
* After the match, damage is applied to `AB()`, again the currently active bot.
Consequences:
1. Enter a competition with a strong bot.
2. Switch to a cheap or already damaged bot.
3. Fight using the strong locked definitions.
4. Apply the wear to the other bot's instances and chassis.
Even accidental bot switching produces nonsensical damage reports.
**Correct model:** every bot needs a stable `botId`. An engagement should store that ID and the exact fitted instance UIDs. Match wear and post-match damage must resolve against the locked bot, not the UI-selected bot. Pilot settings may remain mutable if that is the deliberate rule.

---
## P0 — Existing saves are silently discarded
The README's explicit rule is "never bump `SAVE_V` without migration." The implementation instead says that all other versions are replaced with a fresh state, and `validState()` rejects anything not exactly version 5.
For internal development this may seem convenient, but it undermines:
* Career persistence.
* Balance testing over several builds.
* Bug reproduction.
* User trust.
* Any claim that automatic PWA updates are safe.
At minimum, implement `v4 → v5`. For future versions, use a migration chain and retain a backup copy of the previous raw state before transformation. A knowingly incompatible development build should show an explicit reset message rather than silently starting over.

---
## P1 — Locked layout and visuals are not the machine used by physics
Three distinct machines can coexist during a locked match:
1. **Homologation:** weighs the actual current layout.
2. **Competition snapshot:** saves `autoArrange(b)`, not the actual layout.
3. **Live renderer:** reads `getLayout()` and current garage colours/stickers every frame.
4. **Physics:** uses the locked auto-arranged layout.
The snapshot discrepancy is visible here. The live renderer then overwrites locked customisation and obtains the current layout rather than the match layout.
This directly violates the stated principle that placement changes CG, colliders and beams.
**Fix:** construct one immutable `MatchBotEnvelope` at launch:
```js
{
  botId,
  build,
  layout,
  colliders,
  stability,
  beamCells,
  instanceIds,
  wearSnapshot,
  visual
}
```
Both engine and renderer must consume that envelope. Nothing in the match loop should consult `AB()`, `S.customize` or `getLayout()`.

---
## P1 — Eight-entry cups are actually 16-entry cups
`cupS` and `ouvS2` declare `size: 8`, while other cups declare 16.
But:
* `engageConcours()` passes `tr.rounds`, not `tr.size`.
* `FORMATS.bracket.init()` always creates the player plus 15 rivals.
* It always specifies four rounds.
* The UI future columns also assume 16.
Thus the UI can announce "arbre 8" while the actual competition is a 16-entry tree.
Parameterise the bracket with `size`, validate that it is a power of two, derive rounds using `Math.log2(size)`, and generate labels from the round count.

---
## P1 — Calibration and free fight violate their reward philosophy
Data states:
* Free fight is an exhibition with no progression.
* Calibration has zero purse and no record.
Yet `endToDebrief()` first credits a generic payout for every match. Only afterwards does it branch by mode. A non-benchmark exhibition win also increments `S.beaten`.
This allows free-fight farming and makes the calibration line economically useful despite saying it is measurement-only.
Avoid inferring progression semantics indirectly from `curMode`. Put explicit policies in tournament data:
```js
rewards: {
  boutPurse: false,
  completionPurse: false,
  recordWins: false,
  damage: true,
  stars: false
}
```
Then have one reward resolver apply them.

---
## P1 — Rendering a locked control changes the pilot
`makeSeg()` resets a locked setting to `ENGINE.OPTS[key][0]`. The surrounding TODO correctly admits this is dangerous because list order does not always match the intended default.
For a software-v0 bot, `chargeDist` is hidden and silently changed from the default `"medium"` to the first option, `"short"`, merely because the VS screen rendered.
This violates a basic boundary: **rendering must not mutate gameplay**.
Separate:
* Stored pilot setting.
* Effective setting allowed by installed software.
* Visible control state.
A locked control should either retain its stored choice for later or use an explicitly declared fallback, without modifying persistence.

---
## P1 — Orbit mode does not orbit
The engine itself documents the defect: the orbit target is calculated, then the later non-charge `else` branch overwrites it with the standoff target. It was measured as overwritten 5,820 out of 5,820 times.
This is no longer harmless technical debt because:
* The UI presents circling as a behaviour.
* Opponent tendency can identify a "circler".
* Software modules bid for orbit.
* Balance conclusions about tactics are therefore based partly on a nonexistent action.
Fixing it will change balance, but leaving it broken also invalidates balance. Correct it behind an engine version or balance flag and rerun benchmarks.

# 3. Product-owner review
## What is working
The product concept is coherent:
* Build a recognisable bot.
* Make physical and behavioural choices.
* Pass technical inspection.
* Enter increasingly structured competitions.
* Receive damage and reinvest earnings.
* Compare against fixed calibration standards.
The move to class-S benchtop robots is particularly effective because the constrained footprints naturally teach trade-offs.

## Product risks
### The game frequently says one thing and does another
Examples:
* Eight-entry cup versus 16-entry implementation.
* "No purse" calibration that pays money.
* "No progression" free fight that increments wins.
* "Locked machine" whose wear and damage belong to another active bot.
* Opponent scouting numbers forcibly display `power: "mixed"` even when the opponent actually fights with speed or torque gearing.
These are worse than ordinary bugs because they damage the player's ability to reason about the simulation.

### Career persistence is not yet a product feature
As long as an update can silently invalidate the entire save, the career cannot be treated as durable progression.

### Progression contains farming loopholes
Free fight can currently produce both money and record wins without the risk structure of a formal competition. Calibration can generate money against known fixed opponents. That will distort economy tests and player behaviour.

### Settings are not always meaningful decisions
The README already reports that "fierce" aggression beats "balanced" roughly 77% of the time and that charging is almost always correct. That means the UI offers apparent strategic depth before the combat system creates enough situations to support it.
I would reduce exposed controls temporarily rather than present dominated choices as strategy. Weapons, directional damage, overheating, retreat incentives and positional objectives can later make those settings meaningful.

# 4. Physics-engineer review
## Strong aspects
The physical layer is considerably better than most small browser games:
* Bottom-up mass and component specifications.
* Motor torque/speed relationship.
* Battery voltage coupling.
* Static versus kinetic traction.
* Grip-limited force.
* Fixed timestep.
* Per-component collision geometry.
* Collision impulse and mass response.
* CG-derived stability supplied by the application.
* Material-dependent structural integrity.
* Deterministic flipping.

## Major physical inconsistency: contact force is non-conservative
The drive force already accelerates each bot. During contact, the engine additionally computes a push force from `bot.push` and directly adds it to the opponent's velocity—without applying an equal and opposite reaction to the pushing bot.
This effectively introduces an extra, non-conservative force at contact. It can:
* Double-count drivetrain capability.
* Create momentum.
* Make mass ratios behave unexpectedly.
* Hide errors in traction and collision tuning.
* Turn leverage state into an unexplained force multiplier.
A more physically coherent model would transmit wheel force through the contact constraint. At minimum, apply equal-and-opposite impulses and ensure the transmitted force is limited by each bot's available traction.

## Energy is a gameplay currency wearing physical units
The UI reports real Wh, but simulation energy is:
```js
packWh × 9 × chassisBatteryFactor × wear
```
while consumption is a fixed throttle rate modified by cooling and motor count. Cooling directly lowers battery drain.
This is not dimensionally tied to motor electrical power, current, voltage sag under load, or motor efficiency. It is acceptable as an abstraction, but it should not be described as physically derived.
A better staged model:
1. Mechanical demand from motor torque and RPM.
2. Electrical demand through efficiency.
3. Battery voltage/current limitation and internal resistance.
4. Heat generation.
5. Cooling affects temperature, not energy consumption.
6. Temperature causes derating or wear.

### Other modeling gaps
* Collision impulse does not generate angular impulse; impacts cannot spin a bot except through commanded steering.
* The deepest overlapping collider pair is used rather than a manifold, which can cause contact jitter or unstable normal selection.
* Normal force and traction do not account for longitudinal/lateral load transfer.
* Motor voltage compatibility and current limits are absent.
* Repeated ballast affects app-derived CG, but engine fallback `cogFactor` reads the selected ballast definition only once, not its multiplicity. Headless and app-hydrated simulations can therefore diverge.
These are not all urgent. The non-conservative contact push and finite-number failure are urgent.

# 5. Game-designer review
## The core building puzzle is good
Footprints, mass, CG, wear, component exposure and competition rules produce an understandable construction space. The game has the potential to make "robot personality" emerge from mechanics rather than arbitrary RPG stats.

## Current tactical space is too shallow
The game already knows this: charging dominates, balanced aggression is a trap, and the advanced arbiter mostly benefits from aggression weighting rather than better situational choices.
That means adding more software tiers now risks selling pseudo-depth.
Before adding more controls, add situations in which different decisions are rational:
* Thermal management and temporary retreat.
* Directional armour and vulnerable components.
* Weapons with range or spin-up.
* Finite traction recovery after wheelspin.
* Opponent weapon arcs.
* Damage-dependent behaviour changes.
* Scoring modes other than ring-out.
* Real orbit/flank behaviours.

## Competition formats need a single generic contract
Bracket, championship, ladder and exhibition currently have partially separate assumptions about:
* Engagement.
* Locked builds.
* Rewards.
* Progression.
* Size.
* Completion.
* Damage.
* Retry behaviour.
This is why the eight-versus-16 and exhibition reward bugs exist. Define one format interface:
```js
init(config, seed)
nextOpponent(state)
recordResult(state, result)
isComplete(state)
rank(state)
```
And one competition policy object governing locks and rewards.

## Hidden player advantages
Championship standings resolve score ties in favour of the player. This may be an intentional accessibility concession, but it should be explicit. Otherwise it compromises the "truthful competition" philosophy.

# 6. UI/UX-specialist review
## Accessibility problems
The viewport explicitly disables user zoom. This should be removed.
Several interactive controls are non-semantic `div`s:
* Language choices.
* Pilot segmented choices.
* Bot and colour cards.
They have click handlers but no keyboard semantics, focus state, `role`, `aria-pressed` or tab navigation.
Other issues:
* Icon-only back and settings buttons lack robust accessible names; the settings title is hard-coded in French.
* Canvas elements have no accessible description or fallback.
* Overlays are not declared as dialogs and have no focus management.
* Focus styling is largely missing. The legacy stylesheet contains one hard-coded, off-palette focus colour.
* Animation has no `prefers-reduced-motion` alternative.

## Removing every French accent is the wrong layer of solution
All translated output is passed through a diacritic stripper because some display fonts render accents poorly.
This degrades ordinary body text, names and accessibility even where the body font supports accents perfectly. Apply an accent-safe display font to problematic roles instead. Do not transform the language globally.

## Internationalisation is incomplete
* `<html lang="fr">` is never updated when switching to English.
* `t()` assumes `STRINGS[LANG]` exists; an invalid saved language can crash translation.
* Competition format labels and bracket rounds are hard-coded in French.
* `invEmpty` is declared twice in both language objects, so the first intended message is overwritten.
* The settings panel still says "v4 instances" although the active schema is version 5.

## Performance issue in live rendering
Every animation frame recomputes the opponent's `autoArrange()` layout, while the player layout is fetched live from garage state.
Layouts, composites and colliders should be created once at match startup and retained in the match envelope.

# 7. Simulation-expert review
## Determinism is promising but incomplete as a reproducibility system
A targeted healthy-build replay produced identical results for the same seed. The engine's own design—fixed `TICK`, independent per-bot RNG and two-pass updates—is appropriate.
But reproducibility requires more than a deterministic engine. A recorded match should preserve:
* Engine/build version.
* Match seed.
* Exact hydrated player and opponent builds.
* Instance wear.
* Layout.
* Derived CG, beam mass and colliders.
* Arena geometry.
* Competition rules.
* Final result and important metrics.
Currently much of this is recreated from mutable application state.

## App and headless simulation do not share one hydration pipeline
The engine does not know footprints or layouts. The app computes and injects:
* `beamCells`
* `stability`
* `colliders`
* wear efficiency
This is defensible, but there must be one pure, testable hydrator used by:
* Browser matches.
* Benchmark tools.
* Imported bot sheets.
* Opponent generation.
* QC.
* Replay.
At present match startup manually assembles that hydration, while other routes use `buildOfBot` or raw engine builds. This makes benchmark/browser disagreement likely.

## Missing invariant tests
Add property/fuzz tests asserting after every tick:
```js
Number.isFinite(
  pos, velocity, angle, battery, hp,
  arenaR, throttleL, throttleR
)
```
Also test:
* Zero battery.
* Zero grip.
* Zero motor force.
* Maximum counts.
* Invalid or partial build data.
* Both bots occupying exactly the same point.
* Torn-off propulsion.
* Permanent flip.
* Very small arena.
* Every chassis/part combination accepted by homologation.
* Mirror fairness with confidence intervals.
The dead-battery failure would have been detected immediately by a general finite-state invariant.

# 8. Software-architect review
## `app.js` is the principal maintainability risk
Static inspection shows approximately:
* 4,048 lines.
* 238 named functions.
* Around 50 direct `onclick` assignments.
* 19 empty catch blocks.
* Extensive global mutable state.
It currently owns:
* Persistence and migration policy.
* Career management.
* Inventory instances.
* Bot assembly.
* Layout and geometry.
* Rendering.
* Navigation.
* Shop.
* Economy.
* Competitions.
* Damage.
* PWA status.
* Import/export.
* Internationalisation.
The engine may be pure, but the application layer has become a god module.

## Presentation performs domain mutations
The most concrete example is `makeSeg()`, but it is symptomatic. `renderHome()` also causes opponent generation and tournament creation. A render pass should not establish domain state unless explicitly orchestrated.
Adopt:
```text
commands → domain reducer/service → state
state → selectors/view models → render
```
Rendering then becomes idempotent.

## Multiple sources of truth remain
Examples:
* `fit` is authoritative, while `equipped` and `counts` are mutable caches.
* Parts have legacy effect fields displayed by `partFx()`, while the simulation uses `PHYS`.
* Match visuals read current garage state while physics reads a snapshot.
* Build construction occurs through both helpers and manual object spreads.
* Service-worker version is duplicated manually in `sw.js` and `renderVersionsTable()`.
The comment "part effect summary, always accurate" is particularly unsafe because it reads legacy `PARTS` effect fields, whereas actual dynamics are derived from the physical reference bank.

## Persistence handling is too silent
`saveState()` catches and ignores all errors. A quota failure or serialisation failure therefore looks like a successful save.
Validation is also incomplete:
* No proper bounds/type checks for `activeBot`, `level`, `bolts`, `lang`, wear or counts.
* A negative active index passes `bootSanitize()`.
* Invalid language survives validation.
* Several recovery catches suppress diagnostics.
Use a schema validator and return a visible save status.

## Local HTML injection
Career names are user input and are interpolated into `innerHTML`. Use `textContent`. This is mostly self-XSS today, but it becomes a real vulnerability if careers are ever imported or synchronised.

## CSS transition is unfinished
`roboclash-ui.css` is a coherent tokenised system, but `styles.css` remains a second global design system with generic names and hard-coded legacy colours.
Finish the migration and delete the residual stylesheet rather than maintaining both indefinitely.

## Service-worker release process is fragile
The service worker:
* Uses all-or-nothing `cache.addAll`.
* Relies on manually bumping a string.
* Serves cache-first indefinitely.
* Uses `ignoreSearch:true`.
* Immediately activates with `skipWaiting()` and `clients.claim()`.
This can create mixed-version sessions: a new service worker controls an existing page whose old JavaScript is already loaded. That is particularly risky when save schemas change.
Generate the cache revision from the build, retain a previous cache until clients reload, and show an "update available—reload" action.

# Recommended correction order
## Immediate stabilisation
1. Guard all numerical divisions and add finite-state assertions.
2. Reject HS core components at technical inspection.
3. Give bots stable IDs and bind competition locks, wear and damage to the entering bot.
4. Snapshot the actual validated layout, not `autoArrange()`.
5. Store match-owned visuals/layout; never read live garage state during a match.
6. Make bracket size truly data-driven.
7. Add explicit reward/progression policies to competitions.
8. Remove all mutation from rendering, especially `makeSeg()`.
9. Fix orbit targeting and rerun balance measurements.
10. Implement `v4 → v5` migration and visible save-error handling.

## Architectural consolidation
Split `app.js` approximately into:
```text
state/
  schema.js
  migrations.js
  careers.js
  persistence.js
domain/
  inventory.js
  bots.js
  competitions.js
  economy.js
  damage.js
assembly/
  layout.js
  colliders.js
  hydrate-match-build.js
ui/
  navigation.js
  garage.js
  shop.js
  competitions.js
  match-renderer.js
  dialogs.js
pwa/
  update-manager.js
```
The most important new abstraction is not merely file splitting. It is a single pure function such as:
```js
hydrateBotForMatch({
  state,
  botId,
  competition,
  lock
}) => MatchBotEnvelope
```
Once that exists, homologation, scouting, rendering, physics, damage, benchmarking and replay can finally refer to the same machine.

## Final assessment
The foundation is **substantially better than an ordinary early prototype**, especially the deterministic engine, explicit invariants and physical data. But the project has reached the point where continued feature work inside `app.js` will increase regressions faster than comments and local fixes can contain them.
I would temporarily stop adding competitions, software behaviours and physical subsystems. Fix the match envelope, competition identity, save migration and finite-state guarantees first. Those are now load-bearing architecture, not cleanup.
