# LOADING — the boot measured, the loading screens, the optimisation, the tree ring (2026-09-14)

The design of a four-session chantier, approved by the user on 2026-09-14 after the study.
S1 LANDED as G406 (this file's "S1" section is what shipped; HANDOVER G406 has the after-numbers).
S2 LANDED as G407 (parallel shader compile in two passes + the placeholder env + the deferred bake, the
road-grade segment index, the height memo + the shared slope stencil, the shakedown memo; cold boot
66 s -> 28 s, warm 26 -> 20 s on the third boot; HANDOVER G407 has the table and what is left).
S2, S3, S4 are OWED, in that order, one per session, each measured first with `node tools/boot_perf.js`
(`--cold` for a fresh shader cache, default warm, `--world jolene` for the island, `--shots`,
`--compare tools/perf/boot_perf_base_warm.json`). The baselines are `tools/perf/boot_perf_base_{warm,cold}.json`
and the S1 result `tools/perf/boot_perf_s1_warm.json`.

## Context

The user: loading is not well managed — the garage shows before shaders/objects have landed (chrome-mirror
aircraft, props and pilot popping in), the world's trees keep streaming and thicken as you fly within 10 km,
transitions are unmanaged. Wants: optimise first (one-time pre-compilation/cache), maximum feedback during
load, rotating screenshots on loading screens, and NO display before it looks good (garage finished before it
shows; the world may compromise a tad).

One premise was wrong: the reference planes are ALREADY on demand (G184 — `src/models/*_model.js` are 3-10 KB
manifests; the bin is fetched on pick in `refplane.js:378`). The boot cost is elsewhere — measured below.

Rulings from the user (2026-09-14, this plan): texture size/format prep in a baker is allowed for every asset
(the as-is rule is about live/raw decimation of external geometry; Mixamo geometry is game-ready, untouched);
world scene built under the roll-out screen; media-only service worker WITH a manual "refresh caches" button
and local/server version numbers shown (sync issues experienced before); delivery order S1 → S2 → S3 → S4,
one chantier per session, each measured with the boot profiler first.

## THE OPTIMISATIONS — short version, with consequences (approved 2026-09-14)

1. **Parallel shader compile** (S2). Today every program is compiled synchronously on first draw (25 s cold).
   Use r186's `renderer.compileAsync` (KHR_parallel_shader_compile is available): the driver compiles on its
   own threads while the loading screen animates. Also stop compiling each hangar material twice (bake the env
   probe with a black placeholder env + dress parts BEFORE the bake so the cache key matches). Consequence:
   cold boot ≈ 18 s → ~8-10 s (estimate, measured after), warm −3 s, ~30-45 fewer programs; the roll-out freeze
   (100-150 world programs) → ~0.2 s. Risk: if scene state differs between compile and first draw a material
   silently recompiles synchronously — the program-count delta in the timeline catches it. `checkShaderErrors=
   false` is NOT a lever (moves the stall to uniform introspection — verified in the vendor source).
2. **Road-grade segment index** (S2). `27_premises.js grade.apply` scans a whole road polyline per terrain
   sample → 6.3 s on the island. Bucket segments in cells; byte-identical output. Consequence: island world
   build 9.9 → ~3.5 s. Risk: none if goldens stay green (pure restructuring).
3. **Terrain sampled once per texel** (S2). `bakeGround` calls `terrainH` ~7× per texel (height + 4-tap slope +
   forestHere + surface) over 512² × 2 bakes. Sample one height grid, derive slope by central differences.
   Consequence: analytic world build 3.0 → ~1.3 s. Risk: a slight slope-edge colour shift (render-only;
   screenshot compare before/after).
4. **Shakedown memo** (S2). The settle runs twice at boot (setAircraft, then syncBuild). Memo by spec hash
   (+ persisted in localStorage keyed by core sha). Consequence: −0.9-1.5 s. Risk: none (deterministic).
5. **World scene off the boot** (S3, per your ruling). `buildWorldScene` moves under the roll-out screen with
   the tree ring prefill, atlas bake, world compile. Consequence: boot −1.3-3 s; FIRST roll-out shows a
   transition (~3-5 s warm), later roll-outs are instant (the ring stays resident).
6. **Tree ring: subset + thinning** (S3). Far chunks become a strict SUBSET of near chunks (hash on the full
   grid index), the complement is added on approach, and a per-instance distance dither thins density
   continuously 3.0 → 4.2 km instead of the 4× pop at 3.5 km. Ring pre-streamed under the transition. Far
   shadow/cover passes get a distance gate (today they vertex-process the whole 9 km ring). Consequence: no
   density pop within the ring; +28 % resident instances (memory fixed by allocating near-ladder meshes
   lazily); worst frame ≤ today's 22 ms (measured). Beyond 9 km unchanged (your "fine-ish very far").
   Analytic world stays at 4 km (fog wall at 5.2 km, terrain plane ±4.5 km) — a longer ring there is the
   terrain chantier, not this one.
7. **Bytes** (S4). (a) Texture prep in the bakers — a shared `encode_tex(img, role, max_px)` in
   `tools/media_lib.py`: diffuse → JPEG q85 ≤ 2048, normal/roughness → WebP q90 ≤ 2048 (JPEG blocks normals),
   sources kept as-is under assets/. Consequence: pilot 53 MB → ~3 MB, walls 18 → ~4 MB, boot ≈ 146 → ~60 MB;
   re-baked names change (content-hashed) so manifests update and GATE MEDIA prunes. (b) A build-time media
   manifest (url, bytes, owner) → true byte progress + prefetch of every garage-critical URL at t=0 (parallel
   instead of serial chains); wall/house/site sets become lazy getters (only the chosen set loads).
   (c) Media-only service worker, cache-first on hashed URLs (immutable → no sync issue possible for media),
   never scripts/pages; the UI shows `build <sha> · server <sha> · media cache N MB` and a REFRESH CACHES
   button (clears the cache, updates the SW, reloads). dev.html never registers it.
8. **Instrumentation first, every session**: `tools/boot_perf.js` (the scratchpad rig promoted; cold/warm/
   island, program counts, screenshots at drop +0.2/2/5 s with a stillness score) and `BOOT.log` marks.

## S1 — LOADING SCREEN + BOOT PHASES + GARAGE READINESS + SCREENSHOTS (LANDED, G406)

Design: `src/viewer/boot.js` (new, no THREE, evaluated ~100 ms into the page, before the vendor) owns
`window.BOOT`:
```
phase(id,label,frac) · run(steps,{set,require,done}) · expect(key,n) · landed(key,ok,what) · img(img,key)
note(text) · frame() · ready() · fail(reason) · show(set,opt) · hide() · whenReady() · log[]
```
- `run` chains sync steps with `setTimeout(next,0)` — in GATE UISMOKE's harness (`tools/test_ui_smoke.js:262-272`:
  immediate setTimeout, stored rAF, any id auto-created) the whole chain runs synchronously; in the browser
  each step is a task, fetch promises resolve between steps, the overlay repaints. Never await/rAF.
- Overlay drops when: all steps ran AND every REQUIRED key balanced (`sky`×2, `env` debounce, `room`, `props`,
  `propTex`, `skin`, `crew`, `crewTex`, `crewBuild`) AND 3 quiet frames. Trees/atlas are tracked, not required.
- Watchdogs: idle 20 s since last event / hard 90 s → `fail()` drops it with a note of what never landed;
  "continue anyway" button at idle 8 s. Timer callbacks check elapsed and never re-arm (inert in the harness).
- Progress = 0.7·Σstep weights + 0.3·landed/expected; ticker from `PerformanceObserver('resource')` bytes.
- Frame 1 (and the env re-bakes / crew rebuild that today form the 2nd 12 s block) render UNDER the overlay.
- Roll-out uses the same overlay (`show('rollout')`, world-set screenshots); return to shed: no overlay (nothing
  is disposed — one frame). `#dfBirth` auto-open waits on `window.FLYDIY_READY` (= `BOOT.whenReady()`).

Files:
- `src/viewer/body.html:5-11` → new `#boot` (`#bootShots` `<!--__SHOTS_SLOT__-->`, `#bootVeil`, `#bootPanel`:
  brand / phase / bar / ticker / note / skip) + `<!--__BOOT_SLOT__-->` before `<canvas id="c">`.

1. `node tools/boot_perf.js --cold`, `--warm`, `--world jolene` BEFORE the edit (baseline in tools/perf/).
2. Edit; `node tools/build.js`; `node tools/run_gates.js` (core) green; `--all` before delivery.
3. boot_perf AFTER: milestone table, program counts, stillness score at drop +0.2/+2/+5 s ≈ 0 (nothing
   changes after the overlay lifts); screenshots eyeballed in the pane (rAF is dead there — use the rig).
4. S3: tree_perf `--fly` POP index and worst frame; S4: fresh-profile vs repeat-visit bytes.
