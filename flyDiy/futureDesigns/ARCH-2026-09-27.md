# ARCH 2026-09-27 — IS THE WEB THE LIMIT? SEVEN CHANTIERS, A CUT LIST, AN ORDER

A study, no game code. It answers the user's questions after the Jolene playtest (`PLAYTEST-2026-09-26.md`):

> "today's world engines felt a lot more capable than that to me... I'm questioning the web choice increasingly."
> "Are all these [technology, architecture] to the level of state-of-the-art engines? Could we ever imagine to have
> larger maps and still get a good performance? Is there anything overly costly that really does not contribute that
> much to either the fun of gameplay or the looks that should be removed? I have the feeling our approach to towns is
> fully wrong, and has shown its scalability limits almost immediately, with a few hundreds of buildings."
> "I'm wondering if we shouldn't texture bake our planes before getting in game for the better texture averaging of
> colors blending, less pixel harshness, lower need for anti-aliasing."

Paths are relative to `flyDiy/`. Line numbers are as of `claude/batch-a-base` 29c10de (G690).
Numbers marked **[§0.2]** / **[§0.4]** are the playtest plan's browser measurements (RTX 3080, 2216x1023, warm
unless stated). Numbers marked **[node]** were measured in THIS session in the cloud container (4 cores, no GPU; the
container's CPU is roughly 1.5x slower than the gamer box's i7 and drifts run to run). Numbers marked **[est]** are
arithmetic on measured inputs, and the inputs are named.

---------------------------------------------------------------------------------------------------------

## 0. THE SHORT ANSWER

1. **The failures the playtest measured are architectural, not the web's.** The same RTX 3080 box runs Jolene
   WITHOUT premises at 60 fps with 16 ms of loop JS and a 22 s roll-out screen [§0.2 w6]; the procedural island in
   12 s [§0.2 w9]. What broke the frame was (a) ~641 unique houses generated on the main thread while playing,
   (b) one material per house finish and hundreds of draws per site, (c) a 70-200-substep solver on the thread
   that also renders. A native engine built that way chokes the same way.
2. **The web does cost something real, in three places**, and this study puts a number on each:
   - **Per-draw CPU.** three.js on WebGL spends ~7 µs of JavaScript per draw and the frame is CPU-bound at 1080p
     with the GPU idle (PERF-2026-09-23 "THE FINDING THAT MATTERS"). A native DX11/Vulkan renderer is several times
     cheaper per draw, and render bundles / indirect draws cheaper still. The web therefore punishes a draw-count
     mistake ~3-5x harder [est]. The cure is the same everywhere: fewer draws (instancing, merging, atlases).
   - **One thread by default.** Nothing in flyDiy's frame runs off the main thread today except two helper
     workers (the bench, `src/viewer/bench_worker.js`; the parked-aircraft decimator, `src/viewer/parked.js:543`).
     Workers are available and cheap: a round trip carrying the aeroplane's node positions costs **0.04 ms**
     [node, §1.6].
   - **Cold start.** No shipped shader binaries: Jolene's compile is 36-37 s cold, 13-15 s warm [§0.2]. Native
     engines ship pipeline caches. This is the one web tax with no full cure (only fewer program variants).
3. **The towns: the generator is right, the runtime use of it is wrong.** A house is 70 ms to build at full detail
   and ~10 700 triangles [node, §1.5]; 641 of them is ~7 M triangles and ~0.6 GB of vertex buffers [est]. MSFS-class
   engines draw towns as a few dozen archetypes × thousands of instances. The generator's place is to MAKE the
   archetypes (chantier 3).
4. **Larger maps: yes, with tiles + cooked or instanced content + streaming; no, with runtime generation.** The
   terrain format already allows tiles (every FDTQ1 tree carries its own bounds); the loader does not (chantier 5).
5. **Baking the aeroplane: yes.** The machinery exists (G569, the parked aircraft's atlas bake). It cures SHADING
   aliasing (rivets, seams, panel lines, decal edges) and cuts ~140 materials to a handful; it does not cure
   GEOMETRIC aliasing (edges, struts, wires), which still needs MSAA (chantier 6).
6. **The order after batch B:** physics worker → worker-built premises with a data cook → the town kit (Metlakatla
   returns) → the aeroplane bake (in parallel) → WebGPU only when measured to be the floor → larger maps when a
   bigger map is actually wanted (§9).

## 2. CHANTIER 1 — PHYSICS IN A WEB WORKER

### 2.1 Today

- `app.js:9557` `loop(ts)`: `PACE.frame(ts)` (`:9426-9535`) owes `pc.steps` solver steps; `:9625-9630` runs, per
  step, `script(1/60)` (the pilot, `:4791`) then `sim.step(1/60)`; then `DAY_CLOCK.tick(simDt)`, `director.frame()`,
  `WATER.setTime(sim.t)`, `CK.frame(...)`; then `WF.worldUpdate(cg)`, then the render. Physics and render SUM.
- The G586 clock, the G612 step-debt guard and the G615 auto-cap recovery all exist because the solver shares the
  thread: a long render frame owes more steps, which make the next frame longer.
- The core already runs in node for every gate (`tools/flight_core.js`, built from `src/core/`), and in two
  browser workers: `src/viewer/bench_worker.js` (the load rig and the crosswind ladder: a Blob worker that
  `importScripts` the built core, is handed the SPEC and rebuilds the aeroplane - `bench_worker.js:1-40`,
  `:256-272`) and the parked decimator (`parked.js:530-560`). **The pattern is proven in this codebase.**
- Readers of the sim on the page (`grep -o "sim\.[a-z]+" src/viewer`): `sim.p` 70, `sim.ctl` 31, `sim.cgPos` 23,
  `sim.out` 15, `sim.eng` 14, `sim.setEngine` 9, `sim.axes` 9, `sim.hydro` 9, `fuel`/`cgVel`/`totalM` 5 each,
  `reset` 4, `stance`/`wheelsOnGround`/`bodyOrigin` 2, `impulse` 1.

- **What moves:** the solver, the pilot's `ap.update` and the non-UI part of `script()` (`app.js:4791-4806`; the
  rail/status/pattern-vis lines stay on main and read the ap snapshot), `record(dt)`'s telemetry (batched back),
  the world's physics half (terrainH, surface, obstacles, climate wind with its day), and the step clock.
- **The day clock:** G586 already ticks it on the sim's time in flight (`app.js:9634`). The CLIMATE reads the day's
  sun (thermals, `09_climate.js:438-458`), so the physics half of the day lives in the worker and the sky's day is
  derived from `snapshot.t` on main: both read the same t by construction.
- **What stays:** everything that draws. `poseModel` (`app.js:3130-3230`) and the flex skin read node positions and
  keep doing so from the view. The view's `axes()/bodyOrigin()/cgPos()` are pure functions of p and the def, so
  they run on main against the snapshot - no new protocol for them.
- **The per-frame message:** ~100-130 nodes × 3 × float64 = 2.5-3 KB of p (float64, not float32: at 30 km from the
  origin a float32 CG quantizes to 2-4 mm, a visible jitter in the cockpit view) + ~0.5 KB of outputs. Measured:
  0.04 ms round trip [§1.6]. Double-buffered transferred ArrayBuffers (ping-pong) - no allocation per frame.
- **SharedArrayBuffer is optional, not required.** It needs `crossOriginIsolated`: COOP `same-origin` + COEP
  `require-corp` (or `credentialless`). GitHub Pages cannot set headers; `sw.js` can add them to the navigation
  response (the "coi-serviceworker" technique). `sw.js` is GENERATED by `tools/build.js` and today handles only
  `/media/` (`sw.js:18-27`), so the change is in build.js's template. Checked: `index.html` loads no cross-origin
  script, style or font (its external URLs are credit links), so require-corp breaks nothing today. Caveats: the
  first visit is not isolated until the worker controls the page (a reload, or the postMessage path for that
  visit); any future third-party embed must carry CORP. **Recommendation: ship postMessage-with-transfer first**
  (it is 0.04 ms, works on file://-less hosts and first visits); add SAB only if a measurement asks.
- **Latency.** The render shows the state one step old (interpolated at T - 1/60 s): +16.7 ms, the pose age the
  prototype measured (11-23 ms, [§1.6]). Today at the 30 cap the frame already shows a state computed at the
  frame's start, 33 ms before the flip. For the autopilot it is irrelevant; for manual flying it is one 60 Hz
  step, the same as a 60 fps game. Extrapolation (no delay, small error) is the alternative if the user feels it.

### 2.3 The frame clock in a two-thread world (G586 / G612 / G615)

- **G586's debt disappears from the render thread.** The worker owns sim time: it steps whenever
  `simT < wallT - t0` (one 1/60 s step at a time, `Atomics.wait` / `setTimeout` between). Render frames no longer owe
  steps, so there is no catch-up spiral: a slow render frame is just a late picture.
- **G612's guard moves into the worker and simplifies.** Dilation is needed only when ONE step costs more than
  1/60 s wall - the physics alone cannot hold real time (the old metal Cessna at 200 substeps was 16 ms a step on
  the taxi in the browser [§0.3 item 3]; after G610 it is ~5 ms [node]). The worker caps its catch-up at N steps and
  reports `dilation` in the snapshot; `FLYDIY_PACE.state()` keeps the same fields.
- **G615's auto cap reads render work only.** Its "one-step work" reading (`app.js:9495`) becomes the render
  thread's frame work; 60 is trialled when the RENDER fits 16.7 ms. The cap is then purely a graphics decision.
- **The rig clock stays.** `PACE.legacy` (webdriver/headless, `app.js:9428-9431`) and file:// keep the inline path,
  byte for byte: the same `for (k < nStep) { script; sim.step }` loop. That is also the fallback when `Worker` is
  unavailable (as `bench_worker.js` falls back).

### 2.4 Determinism and the gates

- Every gate keeps running the core synchronously in node: nothing in `src/core/` changes shape. The worker is a
  HOST around `sim.step(1/60)` + `ap.update(1/60)`, in the order the loop runs them today.
- The game was never wall-clock deterministic (G586 maps wall time to steps). What the worker adds is a clean
  replay point: inputs are applied at step boundaries stamped with the step index, so the flight recorder (G620)
  can log `(step, ctl)` and a node replayer reproduces the flight to the bit.
- **A new gate (cheap, core):** the worker host driven by `worker_threads` in node with a scripted input list must
  produce the same FNV hash of p and v as the inline loop over N steps (the probe already does 90 % of it).

### 2.5 Migration

1. `src/core/`-side nothing; a new `src/viewer/sim_host.js` (the worker body, loads the built core as
   bench_worker does) + `sim_view.js` (the main-side read API over snapshots) + the node gate above. Node only.
2. `app.js` behind a flag (`?simw=1`, default off): `loop()`'s step block becomes "post inputs, take the newest
   snapshot"; every `sim.ctl` write becomes a command (INP.write, script's brake). Fallback = today's loop.
3. The world in the worker: a trimmed island boot (the height trees and four u8 grids; fetched through the same
   cache-first `sw.js` path, so no second download), the premises record, `setDay`. The obstacles the VIEWER
   registers (`hitAdd`/`shapeOf`, `render_premises.js:1617-1680`; the hangar; the parked aircraft) are posted as
   rasters - or, after chantier 2, cooked and loaded by the worker itself.
4. Reset / roll-out / fly-on / manual toggle / load test (the bench keeps its own worker) / editor edits.
5. The recorder: the worker's step ms and dilation into G620's rows; `rollout_perf.js` reads them.
6. Flag on by default after a user playtest; SAB/COI as an optional follow-up.

### 2.6 Risks

- **Two copies of the world** (main draws, worker collides). They must be built from the same record and the same
  premises version; an editor edit has to reach both (a version counter in every snapshot, asserted).
- **Hidden sim writers** on main that the grep misses (a panel button writing `sim.fuel`, the stand's control
  sweep writing `sim.ctl` in the shed, `app.js:9597-9603`). The shed can keep a local, non-stepping sim view.
- **Memory:** a second copy of the physics-relevant world, ~70-80 MB [est] (not the 638 MB of the full node
  harness). With SAB the height tree could be shared, but only with COI.
- **Debuggability:** a worker's errors do not reach the page's console the same way; the snapshot carries a
  `diverged` flag (G130's check, `app.js:9638-9643`).

### 2.7 Cost and gain

- **Cost: 4-6 sessions** (host + view + gate; app.js integration; the world and obstacles in the worker; commands and
  edge cases; the clock + recorder; the default-on playtest).
- **Gain [§0.4 → expected]:** the taxi's loop is 18-24 ms = solver 6-11 + render 9-10 + the rest. Without the
  solver on the thread the loop is ~12-13 ms: **60 fps at the stand and taxi on the reference box (R3 ≥ 50 met)**
  and the alu Cessna's solver p90 of 70 ms never reaches a frame. In the node prototype the worst frame falls from
  59-71 ms to 18.5-19.4 ms at 60 Hz, and from 102-125 ms to 33.6-34.2 ms at the 30 cap [§1.6]. The render thread's
  physics cost falls from 3-23 ms median to **0.02-0.03 ms**. It also takes the island decode for the sim (part of
  the world step's 3.9 s) off the main thread.

### 3.1 Today

  cannot be cut: 100-200 ms is one frame of that length every 1-2 s while a site streams in [§0.4 item 5].
- The per-cell optimizations run at runtime (G592): the far-town merge (`hlodCell` `:1267`), the TARR arrays built on
  the CPU by canvas `getImageData` (`house_tarr.js:274-308`, ~84 MB of arrays with mips, G574), the lot and road
  merges, the box rung (G594).
- The composed terrain the solver and the ring read is evaluated analytically; G614 built the height raster
  (A h + B per 16 m tile) but left it OPT-IN because a tile bakes in 1-1.6 ms and the world's own make-time walks
  bake 1 100 of them (+1.2 s).
- `tools/world_prep.js` bakes the TERRAIN pack only (17 files, one gzip stream each, content-hashed under
  `media/world/<id>/`, one manifest `src/core/world_packs.json`); it knows nothing of the premises.

### 3.2 Target — cook DATA offline, triangles only where they are shared

The honest constraint is BYTES. Cooking every unique house as triangles is ~380 KB quantized each [§1.3]: the
village's ~95 houses ~36 MB raw (~20 MB gz), Metlakatla ~130 MB gz - against a 48.7 MB world pack, and every re-cook
writes that into git history for ever (world_prep's own warning, `tools/world_prep.js:44-47`). So the cook has two
tiers:

**(a) The data cook** - `tools/premises_cook.js`, a sibling of `world_prep.js`, run in node (every generator already
runs in node: `tools/_house_check.js:80-95`), writing into the pack per 256 m cell (`LIVE_CELL`,
`render_premises.js:2072`):
- the composed placements: each house's resolved `P` after `placeHouse`, its frame, its plot's dressing plan (fences,
  paths, props, the outbuilding's P) - kilobytes;
- the obstacle rasters (today a vertex walk per house on the main thread);
- the composed-terrain raster tiles (G614's A, B), baked offline - the reason G614 is opt-in (1-1.6 ms a tile at
  runtime) disappears, and the solver/ring read it by default;
- the lot grounds and the road/pavement geometry (small, and the same for every player);
- the TARR texture arrays pre-assembled (KTX2, or raw layer blobs) - no canvas `getImageData`, no 84 MB CPU pass,
  and with GPU compression (BC7/ETC2 via Basis) ~4x less VRAM.

**(b) Geometry, generated in a WORKER from the cooked P, cached in IndexedDB** (the G569 pattern:
`parked.js:636-663`). `HG.build` is a pure function of P (the gate proves it by running headless); the worker returns
transferable typed arrays (positions, normals, uv, AO, lit, slot) and the page only makes a `BufferGeometry` and
uploads. Houses past 150-200 m use the generator's own **lod 1** (10.8 ms, 1 000 tris [§1.2]); lod 0 only near.

**(c) Triangles offline only for what is shared** - the kit's archetypes (chantier 3), the parked stock aircraft
(keys `arch:`/`stock:` are deterministic, `parked.js` header "KEYS"), landmark buildings if wanted.

The page then streams cells by aircraft distance (the G591 stream, unchanged in shape) and **generates nothing on
the main thread**; its per-item work is an upload, sliceable to the 2-3 ms bank.

### 3.3 The editor's live path

The premises editor (`PREMISES_HOST_OPEN`, `render_world.js:5205`; `rebuild(dirty)`, `render_premises.js:2267`) keeps
the live composer. An edit marks its cells dirty: their cooked data is dropped and they fall back to the live
compose + worker build until saved; the save re-cooks those cells CLIENT-side (the cook is the same node-proven
code, run in the worker) into IndexedDB keyed by the record's hash. The shipped cook is regenerated by the tool when
the fixture changes. The G590 `dropPlaces` / `restorePlaces` machinery (`27_premises.js:605-616`) shows the record
side already tolerates a filtered view.

### 3.4 Migration

1. The worker build: `HOUSE_GEN` + kit + the village's `placeHouse` in a Blob worker; `buildHouse` becomes async
   (a placeholder box until it lands - the G594 box is already written); IDB cache by `(generator version, P hash)`.
   Lod 1 past 150 m. This alone removes every 100-200 ms hitch and moves the 24 s town step off the main thread.
2. `premises_cook.js`: placements + obstacle rasters + dressing plans per cell, a manifest key per cell, GATE: the
   cooked placements equal a live compose on the fixture (the premises gate's hash style, G555).
3. The terrain raster offline (G614's tiles into the pack; the analytic path stays the editor's and the gate's
   reference - GATE PREMRASTER already holds the tolerance).
4. TARR arrays offline.
5. The obstacle rasters loaded by the physics worker (chantier 1's step 3 simplifies).

### 3.5 Risks

- **A stale cook.** The cook must be re-run whenever the generator or the fixture changes; a gate compares a cooked
  cell with a live build (hash of the placements, not of triangles).
- **IndexedDB eviction / quota** (Chrome gives an origin a share of the disk; Safari is stricter): the cache is a
  cache - a miss rebuilds in the worker.
- **The worker's generator needs the textures' METADATA** (the finish tables; `house_tex.js`), not the images - the
  geometry does not read them (the gate's stub THREE proves it).

### 3.6 Cost and gain

- **Cost: 5-8 sessions** (1-2 the worker build + lod 1; 2 the data cook + gate; 1 the raster; 1 TARR offline; 1 the
  editor path).
- **Gain:** the roll-out's town step **24.3 s → a few seconds of uploads** [est: the near 4 km's houses as lod 1
  + ~20 lod-0 houses near the stand]; no 100-200 ms frame when a site streams in; the solver's premises ground on the
  raster by default (G614: -4-7 %, the ring's premises queries off). Download: kilobytes for (a), ~0 for (b); the
  first visit pays the worker's generation in the background (641 × 10.8 ms lod 1 ≈ 7 s of worker CPU for all of
  Metlakatla [est]).

## 4. CHANTIER 3 — TOWNS AS AN INSTANCED KIT

### 4.1 Today

Every house is unique: its own P (sampled by `placeHouse` from the zone's rules), its own finish, its own AO bake,
its own stance fitted to its slope. TARR (G574) already turned a cell's houses into "a handful of draws" by moving
finishes into a texture array + a per-vertex SLOT; the far town (G559) merges cells; the box rung (G594). What it
cannot fix: the triangles and the build time are per house.

### 4.2 Target

- **20-40 archetypes** generated OFFLINE by the same generator, chosen to cover the zone's distribution: footprint
  class (S / M / L) × roof family (gable, hip, saltbox, gambrel, shed) × storeys (1, 1.5, 2) × stance (slab, cripple,
  posts) - the presets already name most of them (§1.2's 41 rows). Each at lod 0 and lod 1 (the generator's own) and
  the G594 box. ~26 MB GPU, ~7 MB gz for 30 [§1.3].
- **One material pair** (plain, glass) - the TARR material, whose SLOT becomes `(role of the vertex) × (the
  instance's finish set)`: the archetype's vertices carry a ROLE (siding, trim, roof, rib, deck, ... - the BAGS,
  `_house_gen.js:128`), the instance carries a finish-set index, and the slot table is looked up by both. Paint
  colour, dirt, age, the dirt line and the weather are per-instance fields (the slot already holds them per house).
- **One `THREE.BatchedMesh` per (material, casts or not)**, holding every archetype's lod 0 / lod 1 / box geometry;
  each house is an instance whose geometry id is switched by distance (lod 0 < 150 m < lod 1 < 1.2 km < box). three
  r186 culls each instance per camera (G585 uses exactly this in `cover_ring.js`). **All 641 houses: ~4 draws in the
  main pass and ~2 in the shadow pass**, independent of the count. Alternative: one `InstancedMesh` per archetype
  × LOD (≤ 30 × 3 × 2 = 180 meshes, most culled): no per-instance JS cull, more draws. Measure both.
- **The instance table** comes from the data cook (chantier 2a): 641 × ~32 B.

### 4.3 What is lost, and how to hide it

- **Uniqueness.** 30 shapes for 641 houses: each shape ~21 times. Hidden by: yaw (any angle the street allows),
  8-12 paint colours × 4-6 finish sets per role, dirt/age, the dressing that stays per lot (fences, paths, yard
  props, cars, boats - already instanced props), a MIRRORED copy of each archetype in the batch (a negative scale
  per instance would flip the winding), a ±10 % stretch along the ridge (UVs are metres, so a stretch shows as a 10 %
  wider board - acceptable, or scaled in the vertex shader). 30 × 2 × ~50 × 4 ≈ 12 000 looks for 641 houses. MSFS's
  autogen works exactly this way.
- **The stance on sloping ground** (the Alaskan layer: houses on posts over the beach, `_house_gen.js:15-17`). The
  archetype stops at its floor; the posts / cripple wall below carry a vertex flag and stretch down in the vertex
  shader to the instance's ground offset at the four corners (four floats a house, from the cook's ground query).
- **Plot-fitted size.** The sampler fits L × w to the plot; the kit picks the archetype whose footprint fits the plot
  best, then yaw. Plots in Metlakatla are 20-34 m wide (ZONE_RULES `27_premises.js:93`) - wide enough for the S/M/L
  classes.
- **Landmarks** (the church, the cannery, named buildings): keep them unique (chantier 2b), 5-20 a town.

### 4.4 Migration

1. The archetype set: a tool that samples the zone rules' distribution, clusters the sampled P, and picks
   representatives; GATE HOUSE's rules hold for each (it already checks lod 0 / lod 1 agreement).
2. The kit pack in `media/` (quantized, gz) + the instance table in the premises cook.
3. The TARR material's role × finish-set slot; the stance stretch; the BatchedMesh host in `render_premises.js`.
4. A dithered LOD cross-fade (A2-FADES' fade applies).
5. Metlakatla's zones switch to the kit; the village and the mine can follow.

### 4.5 Risks

- **The look.** The user will judge repetition by eye; the first milestone is a side-by-side of one street,
  unique vs kit, before anything else is built.
- **BatchedMesh's JS cull** walks every instance per pass (G585's note: "COST MOVED, NOT MEASURED"): 641 instances
  × 3 passes ≈ 2 000 tests, ~0.1-0.3 ms [est]. Measured on the box before choosing it over InstancedMesh.
- **The shadow pass** draws the batch again; with per-instance culling it draws only what the shadow camera sees.

### 4.6 Cost and gain

- **Cost: 5-7 sessions** (archetypes; pack + instances; material + stance; host + LOD; the look review).
- **Gain [est, §1.3/§1.4]:** Metlakatla from ~0.6 GB of vertex buffers to ~26 MB; from hundreds of draws while it
  streams (and ~2.5 ms of extra render CPU even as far boxes, [§0.4] `?town=1` 12.4 vs 9.9 ms) to ~6; its load from
  minutes of streaming at 3 ms a frame [§0.4] to one pack decode (~7 MB) and a sliced upload.

## 6. CHANTIER 5 — LARGER MAPS

### 6.1 What the pack is today

- **Terrain:** two FDTQ1 quadtrees (near `e2`: 5 m source, `maxDepth` 13, 14 896 leaves, 22 MB decoded; far `e4`),
  each over ONE square of side 39 195 m (`world_packs.json` headers). FDTQ1 is a preorder bit topology + one gzip
  stream of patches decoded SEQUENTIALLY (`src/core/19_terrain_codec.js:158-200`): no random access into a subtree.
- **Grids:** 3 095 × 3 920 cells at 10 m (~1 210 km²), one raster per layer (u8 × 8 layers, RGB albedo and tint;
  12.1 MB / 36.4 MB decoded each).
- **The whole island is decoded at boot:** 238 MB raw, 48.7 MB shipped - ~40 KB shipped and ~200 KB decoded per km².

### 6.2 What larger means [est, at Jolene's density]

| map | shipped | decoded if loaded whole | verdict |
|---|---|---|---|
| Jolene (~1 200 km²) | 49 MB | 238 MB | today |
| 50 × 50 km (2 500 km²) | ~100 MB | ~0.5 GB | monolith borderline |
| 100 × 100 km (10 000 km²) | ~400 MB | ~2 GB | **only as tiles** |

### 6.3 Target

- **Tiles.** A tile is simply another FDTQ1 tree (the header already carries `bounds` and `side`), e.g. 8 km
  squares, sharing edge samples (the patch is 32 + 1 samples, so neighbours share the edge row). The grids per tile
  the same way. `world_prep.js`'s SET becomes per-tile keys; the manifest lists tiles; the loader fetches by distance
  (a resident ring of ~16-24 km radius) - the premises stream's shape, applied to terrain.
- **The colour grids become GPU textures**, compressed (KTX2), not CPU arrays: albedo + tint are 30 % of the decoded
  bytes and the physics never reads them.
- **Precision.** Physics is float64 (`30_solver.js:114`): no issue at any map size. Render is float32 on the GPU:
  three.js forms model-view in double on the CPU, so a mesh with a LOCAL origin is exact; geometry baked in WORLD
  coordinates is not - the TARR merge (`house_tarr.js:13`, "world space"), the pavement's `vPavW`
  (`pavement.js:531`), `geo.translate(a.x, 0, a.z)` (`render_world.js:5338`). float32's step is 1.95 mm at 16-32 km,
  3.9 mm at 32-64 km, 15.6 mm at 128-256 km. Jolene (≤ 30 km from the origin) is fine; **past ~60 km, rebase the
  render origin** (the scene root offset by a tile multiple when the aircraft crosses a threshold; physics
  untouched) and bake geometry cell-local (chantier 2's cells already are).
- **Content must be cooked or instanced** (chantiers 2-3): runtime generation scales with the map, and a few
  hundred houses already saturated the frame.

### 6.4 Cost, risk, gain

- **Cost: 8-12 sessions** (tile format + prep; the streaming loader; seams + far LOD across tiles; textures; origin
  rebasing; the premises across tiles).
- **Risk:** the git-hosted media: every re-bake of a 400 MB map is 400 MB of history; GitHub Pages recommends
  < 1 GB published. A bigger map probably wants a CDN / release-asset host (the loader only needs URLs).
- **Gain:** boot cost independent of map size (only the ring decodes); memory bounded by the ring. **Do it when a
  bigger map is actually on the roadmap - not before chantiers 1-3.**

## 7. CHANTIER 6 — TEXTURE-BAKED AEROPLANES

### 7.1 Today

- The flown model: 247 meshes on 142 materials; a world scene render draws it 231 times + 208 in the shadow pass
  (G576). AEROSKIN materials are pooled per LOOK (`aeroskin.js:3708` `AERO_POOL`), `MeshPhysicalMaterial`
  (`:4082`), with the livery, weathering (AERO_WX), rivets, seams, panel lines and relief computed in the fragment
  shader - partly AA'd analytically (10 `fwidth`/`dFdx` uses in `aeroskin.js`), the rest aliasing at distance.
- **G569 already bakes an aeroplane** for the parked ones (`parked.js:65-80`, `:666-1105`): welded, cut into charts,
  packed into one atlas (1024², ~1.4 cm a texel on a C172's 97 m²), then the FLOWN SHADER drawn in atlas space
  writes albedo, normal (object space), clear coat / roughness / metalness; one material, one draw a level; kept in
  IndexedDB (`flydiy.parked`, store `bake`, `:636-663`). Measured: 2-3 s a capture on the reference box [§0.4],
  2.5-6 s a build [PLAYTEST §1.1 item 5].

### 7.2 Target

- **Bake at roll-out, cached per build** (key: the spec's content hash + the game build id), or in the garage on
  save in idle time. The garage keeps the live shader (the livery editor needs it); the flown aeroplane in the world
  draws with ONE baked material (+ glass, lamps, crew, the prop disc).
- **2048² atlas** (~0.7 cm a texel [est from G569's 1.4 cm at 1024]) - a chase-camera pixel at 10 m is ~1.2 cm at
  1080p. For the cockpit view (the wing 1-2 m away) add a tiling DETAIL normal / grain map, or keep the live shader
  under ~5 m (a LOD by distance). A/B screenshots decide.
- **Tangent-space normals**, not G569's object space: the wing flexes and the surfaces hinge (object-space normals
  are only right for a rigid parked aircraft).
- **Draws:** 142 materials → ~4. Meshes fall only as far as motion allows: parts that hinge and buckets the flex
  writes stay separate (`mergeStill`'s rules, G576) unless merged into ONE skinned mesh with a bone per rig and hinge
  (three's SkinnedMesh; the flex is already CPU-written vertices). Target ~10-20 draws a pass instead of ~230.
- **AA, honestly:** mipmaps prefilter the albedo and roughness, so rivets, seams, panel lines and decal edges stop
  shimmering at distance ("less pixel harshness" - yes). Bake Toksvig-adjusted roughness into the mips to also
  tame SPECULAR aliasing from the normal detail. What it does NOT fix: silhouettes, struts, wires, the prop - that is
  geometric aliasing, and MSAA (or a TAA) is still the tool. So: less need for AA on the surfaces, not none.
- **Where the bake runs:** an `OffscreenCanvas` with its own WebGL2 context in a worker (Chrome, Firefox, Safari
  17+), so the 2-6 s never freezes the page; the main-thread path stays as the fallback (as G569 has).
- **IndexedDB:** 2048² × 3 maps RGBA8 = 48 MB raw a build; stored as PNG/WebP blobs (~6-12 MB [est]) or KTX2; keep
  the last N builds.

### 7.3 Risks

- The livery's projector frame (`uCraftInv`, `app.js:3157-3170`) and the decals are baked in - a livery edit means a
  re-bake (it happens in the garage anyway).
- Features that depend on the camera or time (clear-coat view dependence, the day's wetness) stay LIVE: the bake
  writes material parameters, not lit colour - G569's rule.
- A chart seam on a flexing wing must not open: the weld + seam-weighted decimation of G569 already handles it.

### 7.4 Cost and gain

- **Cost: 3-4 sessions** (the flown bake on the G569 machinery with tangent space; the one-material flown model and
  the skinned merge; the worker/OffscreenCanvas + IDB; the look A/B).
- **Gain [est]:** ~400 fewer draws a scene render → **~2.8 ms of render CPU at ~7 µs a draw** (PERF-2026-09-23), more
  in the passes that draw the aeroplane again (the near shadow map, the mirror); fewer program variants to compile;
  steadier surface detail at distance. The bake itself costs 2-6 s once per build, off the main thread.

## 8. CHANTIER 7 — WEBGPU

### 8.1 Today

`vendor/three.webgpu.min.js` (1.1 MB) is vendored and `dev.html?tsl=1` boots the game on `WebGPURenderer` (the
WebGL2 backend; `?tsl=gpu` for WebGPU) - `tools/build.js:708-730`. **But WebGPURenderer ignores `onBeforeCompile`
and cannot draw a `ShaderMaterial`** (HANDOVER, W0.5b "THE FINDING"). flyDiy has **72 `onBeforeCompile` hooks in 21
files** (render_world 18, the house generator 10, trees 5, parked 5, aeroskin 5, render_premises 4, ...) and **23
`ShaderMaterial`s in 10 files** (clouds 7, atmo 4, water 2, spray 2, hangar 2, ...). Every one is a TSL port.

### 8.2 What it would give

- **Render bundles** (static draws recorded once, replayed at near-zero JS cost): the terrain, the premises, the
  hangar - the ~7 µs/draw JS floor [PERF-2026-09-23] mostly goes for static scenery.
- **Compute culling + indirect draws:** BatchedMesh/instancing culled on the GPU (the JS cull of G585 goes); the
  grass and cover ring grown and culled in compute; LOD selection per instance on the GPU.
- **Fewer state changes / storage buffers** (the TARR slot table becomes a storage buffer, no float texture).
- **Compute for the water field and the clouds.**

### 8.3 What it costs

- **12-20 sessions** [est]: 95 GLSL touchpoints, the biggest being the splat ground, pavement, water, clouds, the
  house shader (shadeHouse / cloudWeather / shadeGlass and TARR's edits), aeroskin, trees; GLSL and TSL side by side
  behind the flag until the last is ported (the W0.5b plan). Risks: three's WebGPU backend maturity, Safari /
  Firefox support (shipping, but younger than Chrome's), the timer queries G620's recorder uses, the reversed-depth
  and shadow-bias work of batch A redone.

### 8.4 When it becomes worth it

After chantiers 1, 3 and 6 have cut the draws and taken the solver off the thread, measure the render submit at
the stand, the taxi and over a town. **If it is still the frame's floor (say > 8 ms on the reference box), or if the
tree/grass density the user wants needs GPU culling, port.** Not before: today the draws are reducible by an order
of magnitude with WebGL tools, and a port of 95 shaders would freeze feature work for weeks.

## 10. THE ONE-PAGE RECOMMENDATION

**Is the web the limit?** Not for this game on this hardware, today. Measured: the reference box holds 60 fps on
Jolene without premises (16 ms loop, 9.5 ms render CPU [§0.2 w6]); everything that broke the playtest was a design
choice that would choke a native engine too - unique houses generated during play, a material per finish, the
solver on the render thread. What the web really costs:
- **~7 µs of JavaScript per draw** with the GPU idle (PERF-2026-09-23): a draw-count mistake hurts ~3-5x more than
  in a native engine [est]. The fix (instancing, batching, baking) is the same one state-of-the-art engines use.
- **No shared-memory threads by default** on GitHub Pages (COOP/COEP only via the service worker); but a plain
  worker's round trip is 0.04 ms [node] - message passing is enough for everything proposed here.
- **Cold shader compiles** (36 s cold): the one tax with no full cure.
- **JS is ~1.5-3x slower than optimized C++ for the solver** [est, not measured]; once the solver is in a worker,
  a WASM port of `30_solver.js` becomes a drop-in option if it is ever the floor.
Against that: a native port (Unity/Unreal/Godot) means re-writing ~64 000 lines of viewer, ~31 000 of core and
~79 000 of generators, the garage UI and the whole gate battery - many months, for a ceiling this project is nowhere
near. **flyDiy uses perhaps a fifth of what the browser can do; the three structural moves of every modern engine -
COOK, INSTANCE, THREAD - are all available on the web and none is done yet.** That is the gap the user feels.

**The order after batch B:**

| # | chantier | sessions | why this position | measured / expected gain |
|---|---|---|---|---|
| 0 | **Quick wins** (can ride batch B): lod 1 past 150 m, outbuildings lod 1, stock parked aircraft cooked | 1-2 | cheap, measurable now | far-town triangles ÷10; 2-3 s a parked build off the roll-out |
| 1 | **Physics in a worker** (§2) | 4-6 | the biggest structural win for the ground phases; ends the step-debt spiral for good | taxi loop 18-24 → ~12-13 ms (R3 met at 60); worst frame 59-125 → 18-34 ms [node] |
| 2 | **Worker-built premises + the data cook** (§3) | 5-8 | reuses 1's worker infrastructure; removes every house hitch | town step 24 s → a few s; no 100-200 ms frames in flight; the terrain raster on by default |
| 3 | **Towns as an instanced kit → Metlakatla returns** (§4, §5) | 5-7 (+1-2 for the lite interim) | needs 2's instance tables; the scalable form of the town | 641 houses in ~6 draws, ~26 MB instead of ~0.6 GB, ≤ 1 ms a frame |
| 4 | **Aeroplane bake** (§7) — in parallel with 2-3 (independent files) | 3-4 | the user's own idea, and it is right for surfaces | ~400 draws → ~20-40; ~2.8 ms render CPU; steadier detail |
| 5 | **WebGPU** (§8) | 12-20 | only if, after 1-4, render submit is still > ~8 ms or density needs GPU culling | render bundles and GPU culling for static scenery |
| 6 | **Larger maps** (§6) | 8-12 | only when a bigger map is wanted; needs 2-3 first | boot and memory independent of map size |

**If only one thing is done: the physics worker.** If two: the worker, then the worker-built premises - together
they make the roll-out and the taxi what the procedural island already is (12-22 s screen, 60 fps), with Jolene's
content, and they build the road to Metlakatla's return.
