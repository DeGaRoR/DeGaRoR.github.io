# flyDiy missions: what exists, and a proposed design (A0, 25 Oct 2026, for discussion)

Source: the user's "Fly DIY — Mission System Specification" (25 Oct), plus a read-only survey of master + L25c. File references are to flyDiy/.

## 1. What we already have

The mission system already exists under the name **contracts**. It is mature, pure-core and gated.

**Record (73_contracts.js:7-33).** A contract is `{id, provider, kind: contract | job | challenge | build | survey, title, brief, stages: [{subs: [{do, from, to, at, load:{kg,pax,bulk,items}, when, crit, medals}]}], pay, rep, unlock, needs, repeat, followUp}`. Stages run in order; the subs inside a stage can be done in any order.

**Verbs.** carry, fly, land, survey, deliver and accept.

**Lifecycle (74_career.js).** offer -> accept -> track -> stop-by-stop resolution -> complete (pay, reputation, unlock). Prerequisites are `needs.after` (ids) and `needs.rep`.

**Providers.** Five organisations with reputation 0-5 and authored arcs. Each provider's client now has a portrait (claude/people).

**Aircraft orders.** `kind: build` with criteria (`CONTRACT_CRIT_KINDS`): seats, empty mass, powertrain, tank, span, cost, g, crosswind, hydro, TAS, endurance, range, take-off/landing at a named strip. Each is backed by a **flown acceptance leg** under stated reference conditions (72_accept.js) and the bench numbers (genShakedown: Vs, cruise, climb, take-off run, range, cost, mass).

**Arrival-relative checks.** The tutorial's Cub job judges the plane against the state it arrived in (79_story.js).

**Rewards.** contractPay: base, km, load, surface, chain, night, plus medal / margin bonuses. Calibrated by econ_sim.

**Generator.** Seeded jobs: p2p, back, onward, milk run, survey loop/pair/transit.

**Freight.** Mass + volume packing, the loading view and strapping. Passengers walk and board (queue coming, G3619).

**Time windows.** Arrive before dusk / after dusk / before dawn / within [h0, h1], night ops, the moon, wait-until.

**World construction tracks (76_stages.js).** A contract's `unlock: {stage}` reveals premises. Note that these are called "stages", which clashes with contract stages; see section 3.

**Also in place.** Hired pilots (with skills, soon on the hire screen); career routes; tech mask; loan job; used market + makers; career-own imports; hangar storage + tie-down spots; occupant injury bands (34_occupant); a crash resets the plane and keeps the contract live; the flight recorder logs position every frame.

### Gaps against the spec

- **Objectives are aerodromes only.** The survey test is a 2D overfly within 450 m. There are no free GPS points, no altitude band, no gates, rings or timers between points, and no per-objective feedback.
- **Aircraft order.**
  - Missing criteria: climb/VS, stall speed, numeric take-off and landing distances, fuel flow, cargo volume, pax.
  - Rule g1 forbids configuration words (engines, push/pull, tail, canopy). That conflicts with the spec's "preferences".
  - A customer-supplied starting plane exists only in the tutorial.
  - A delivered airframe stays in your fleet; it is never handed over.
- **Transport.** No departure time and no max duration (GQ17 ruled deadlines out). No setup from a drawn route.
- **Speed.** Only timed A->B from the logbook. No gates or balloons. **Rally and acrobatics: nothing.**
- **Multi-stop.** No per-stop embark conditions, no per-stop narrative (the authored `.done` texts are never shown), and no parking-spot objective.
- **Failure.** Occupant bands are not read by contracts, freight cannot be harmed, there is no graded damage assessment and no explicit fail/restart.
- **Economy.** Profit is implicit, and airframes cannot be sold (only hangars resell at 0.5).
- **Tutorial skip.** Only T1 can be skipped. The PA-18 floats build exists but nothing references it, and it is not a validated design.
- **Authoring.** Contracts are JS literals in 72_contract_data.js. There is no JSON pack, no loader, no version field, and no editor. Drawn routes live in per-browser localStorage.

## 2. Principle

Extend the contract record; do not build a parallel mission system. Everything above (pay, providers, reputation, needs, acceptance, freight, crew, night, construction reveals) keeps working, and the new mission kinds become new step verbs and new place types.

## 3. The data model (proposal)

### 3.1 One "place" type for every objective

```
place = { field: 'w3' }                                        // an aerodrome (today)
      | { pt: [x,z], r: 150, alt: {min,max,ref:'agl'|'msl'} }  // a survey point / checkpoint
      | { gate: [[x1,z1],[x2,z2]], alt: {min,max}, prop: 'balloons'|'pylons' }   // a line between two posts
      | { ring: [x,y,z], r: 8, dir: deg, prop: 'donut' }       // a 3D ring
      | { spot: 'tie-down id' }                                // a parking spot (fleet spots)
      | { site: 'site id' }                                    // a construction site (see 3.5)
```

### 3.2 Steps (today's "subs")

```
step = { id, place, do: carry|fly|land|photo|pass|park|deliver|accept|wait|talk,
         load: {kg, pax:[ids|count], bulk, items}, embark: [...], disembark: [...],
         require: {when, before, maxMin, plane:{...crit}}, say: {who:'personId', text},
         onDone: {say, pay, unlock, site:{id, state}} }
```

- **photo:** inside the place's radius and altitude band -> the shutter sound + a message (the user: sound only, plus the message; the narrative asks for pictures).
- **pass:** through a gate or ring, in the right direction.

### 3.3 Timers on a group of steps

```
timer = { start: stepId, stop: stepId, target: seconds | 'refSpeed:kmh', splits: true, medals: [...] }
```

| Mission | Timer | Shown to the player |
|---|---|---|
| Speed | 2 gates, start on gate 1, stop on gate 2 | the target |
| Rally | checkpoints (pt places) with split targets | coordinates + target times only |
| Acrobatics | a ring course, start on ring 1, stop on the last | the target |

For a rally, the course comes from a drawn route EMBEDDED in the mission (its pts, not a localStorage id). The split targets are either authored or derived from route length / reference speed.

### 3.4 Rules (completion and failure)

```
rules = { crash: 'fail', injury: 'fail', freight: 'fail', damage: 'assess' }
```

Damage is assessed at the end. A mission fails only on a full crash, any person harmed, or freight harmed; on failure the player is offered a restart. The occupant bands are reused. Freight harm needs a new freight-damage rule; it is "no load failure" today.

### 3.5 Sites (hook for the deferred construction project)

```
site = { id, asset: 'meteo station', at: {x,z,hdg}, state: 'planned'|'building'|'built' }
```

A step can move a site's state, and a state maps onto a world construction track reveal (76_stages). That way a mission can say "deliver the steel to the meteo station site" today, and the big phased construction project later is just a campaign whose steps advance sites.

### 3.6 Aircraft orders

- **New criteria:** climbMs, stallKmh, toDistM, ldgDistM, fuelLph, cargoL, pax.
- **Preferences** (engines, push/pull, tail, canopy, suspension) become bonuses, not requirements. Rule g1 changes from "forbidden" to "bonus only".
- **`startFrom`:** a build file or 'player'. This generalises the tutorial's arrival-relative checks.
- **On delivery:** the airframe is handed over and leaves your fleet. Profit = pay - materialise cost, shown on the card.

## 4. Structure: three options for how missions chain

| Option | Shape | Pros | Cons |
|---|---|---|---|
| **A. Flat + prerequisites** (today) | each mission has `needs: {after: [ids], rep}` | simple; generator-friendly; already coded | a campaign is invisible (you read it by following ids); authoring a 20-mission story is error-prone |
| **B. Tree with order rules** | Campaign -> Chapter -> Mission -> Leg -> Step; each container has an `order: seq \| any \| choose:N`, and optional `needs` cross-links between containers | maps 1:1 onto an editor tree; today's stage (seq) and subs (any) fit as-is; story arcs and the construction project are campaigns; generated jobs stay campaign-less | cross-campaign dependencies need the `needs` escape hatch |
| **C. Graph of steps** | the whole campaign is one flow chart of steps with conditions | most expressive (branches, fail paths) | hardest to author and to validate; hard to show to a player |

**A0's recommendation: B, keeping A's `needs` as the escape hatch.** It is a superset of what exists, so nothing is thrown away. Renames:
- today's contract "stages" become **legs** (ordered) and "subs" become **steps**;
- the world construction "stages" keep their name.

A Mission is what the player accepts and is paid for; a Chapter groups missions (e.g. "The mine reopens"); a Campaign is a provider's arc, the story, or the construction project.

## 5. The external editor

A pure-UI web page with no 3D. The cloud can build it, since it needs no graphics box.

- **Format.** It reads and writes a **mission pack**: JSON, `{what:'flydiy-missions', v:1, campaigns:[...], missions:[...]}`, in `src/missions/*.json`. The game loads the built-in packs and, later, packs the user imports.
- **Validation.** It loads the game's own core (contractNormalise / contractValidate / contractPay), so editor and game always agree, and it shows the reward live.
- **Layout.** A tree on the left (campaign / chapter / mission / leg / step). A form on the right. A 2D map picker built from the island's map pack, to click points, gates and rings (altitude fields) and parking spots. A route importer for exported drawn routes. A card preview with the owner's portrait.
- **Authoring.** People are chosen from the people table, so narrative speakers are real characters. Texts are authored by the user, not generated.
- **Gate.** GATE MISSIONS validates every pack.

## 7. The user's decisions (25 Oct ~23:30)

- **Structure B: YES.**
- **Old contracts:** each is retrofitted into the new model or dropped. The TUTORIAL missions stay exactly as they are; they appear in the list marked "tutorial / phase 0" and cannot be edited.
- **The mission file + editor is a DEV TOOL for now.** It may get a link under the game's Dev section later; packs are not player-importable yet.
- **Rally:** checkpoints and split targets are worked out automatically from the hidden route, and the author can override them.
- **Aircraft preferences:** each item is marked by the author as **bonus** or **mandatory** ("If I wanted 2 engines, I would be upset with 1 only" - so engine count and the like can be mandatory).
- **Delivery:**
  - We paid to manufacture the plane; it is sold to the client at a higher price and is no longer ours.
  - The BLUEPRINT is saved automatically, so the plane can be rebuilt, or imported in sandbox mode.
- **Max duration / departure time:** they are in the user's spec, so they are allowed (this reverses GQ17 for missions that set them).
- **Injuries:** already evaluated. DMG-OCCUPANT (G2373-G2377, Deform) landed in L25b, 25 Oct; the crash card shows the occupant bands. Mission rules READ those bands (the "survival: vague only" tone rule stands).
- **The tutorial's Cub, in this order:**
  1. a J3-like Cub waits at the WWII hangar;
  2. upgraded to Super-Cub-like specs (the validated Cub sits about midway);
  3. a couple of missions;
  4. fitted with floats for a contract (the PA-18 floats build is that state);
  5. assigned to a route with a hired pilot - the tutorial's end.

  So the **full skip** starts right after that route is established, with the floats Cub on its route. All three versions get validated (J3, Super-Cub-like, floats); the user may supply the 3 files.
